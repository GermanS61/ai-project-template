# PROJECT INIT PROMPT

Используйте этот prompt после создания нового репозитория из шаблона и первоначального заполнения `PROJECT_BOOTSTRAP.md`.

```text
Ты начинаешь новый программный проект в этом GitHub-репозитории.

Сначала прочитай и соблюдай `AGENTS.md`.

Затем изучи `PROJECT_BOOTSTRAP.md` и текущие файлы репозитория. Не начинай сразу писать большой объём production-кода.

Твоя задача на этапе инициализации:

1. Восстановить точную цель проекта, пользователей, основной сценарий и ограничения.
2. Найти противоречия, критические неизвестные и скрытые предположения.
3. Если неизвестное не блокирует безопасную архитектуру — пометь его `TBD`, сделай разумное предположение и продолжай. Критические продуктовые развилки вынеси на решение владельца проекта.
4. Определить минимальный MVP.
5. Определить Working Skeleton — самый маленький полноценный end-to-end механизм, который можно запустить и проверить.
6. Выбрать только подтверждённые требованиями режимы работы (standalone, embedded/integration) и точки расширения. Для неприменимых вариантов указать `N/A` с причиной; не создавать под них контракты и abstraction layers заранее.
7. Персонализировать репозиторий: заменить шаблонные название и описание, заполнить в `README.md` актуальные команды запуска, тестов и линтера, описать конфигурацию, удалить или адаптировать template-only инструкции и существенные placeholders. Отдельно запросить решение владельца о лицензии; не выбирать и не наследовать её молча.
8. Обновить `SECURITY.md`: указать применимую политику и реальный приватный канал сообщения об уязвимостях. Если канал ещё не выбран, зафиксировать это как блокирующее решение владельца, а не оставлять публичный placeholder.
9. Обновить `ARCHITECTURE.md` только подтверждёнными компонентами и границами.
10. Разбить работу на проверяемые этапы в `PROJECT_PLAN.md`. Stage 0 должен завершиться согласованным и валидированным комплектом документации, а начиная со Stage 1 проект после каждого этапа должен оставаться работоспособным. Для каждого этапа определить базовые проверки, безопасность, наблюдаемость и сохранность данных либо обоснованное `N/A`. Если этапы адаптированы, синхронизировать варианты Stage в `.github/ISSUE_TEMPLATE/implementation_task.yml` и поле `Stage` GitHub Project.
11. Обновить `ROADMAP.md`: в roadmap включать только принятый scope. Не превращать идеи автоматически в обязательства.
12. Если существенное архитектурное решение требует фиксации — создать ADR в `docs/decisions/`.
13. Подготовить первоначальный backlog: Implementation Tasks отдельно, Feature Requests/Research отдельно. Создавать Issues в GitHub только если текущий запрос явно разрешает внешнюю запись; иначе представить черновики владельцу проекта.
14. Для каждой задачи определить acceptance criteria и воспроизводимый способ проверки.
15. Сначала завершить Stage 0 — Architecture / Bootstrap: согласовать паспорт проекта, персонализировать репозиторий и подготовить архитектуру, план, backlog и нужные ADR. Затем перейти к Stage 1 — Working Skeleton и реализовать минимальный end-to-end путь.

Перед кодированием покажи краткое резюме:
- что мы строим;
- MVP;
- Working Skeleton;
- выбранные режимы работы и обоснованные `N/A`;
- архитектурные модули;
- результаты Stage 0 и план Stage 1;
- ключевые риски;
- вопросы, действительно требующие решения владельца.

После этого работай через отдельные ветки и PR согласно `CONTRIBUTING.md` и `AGENTS.md`.
```
